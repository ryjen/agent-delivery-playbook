## What v0.1.0 is

The first versioned, portable **Agent Delivery Playbook** package for bounded, reviewable AI-assisted software delivery. It supplies independent-of-provider guidance, structured task envelopes, a risk/evidence model, examples and reproducible structural validators. It is **not** an agent runtime, production policy engine, signed approval service, standalone CI provider, or automated release system.

## Highlights

- **Risk-shaped task governance.** T1–T4 risk tiers, E1–E4 evidence coverage (with source trust/binding/independence considered separately), scoped tool/effect authority, context provenance and accountable review.
- **Portable contracts and templates.** Task-envelope JSON Schema with strict fields, example envelopes, minimum adoption kernel, PR template, reviewer guidance, identity/capability design, and replayable evidence documentation.
- **Reproducible validation.** Pinned Nix development/check environment; lightweight and PyYAML/JSON Schema envelope validation, unit/negative tests, glossary consistency and repository-integrity checks.
- **Adversarial and configuration-regression examples.** Deterministic synthetic fixtures for selected bypass and regression scenarios; these are **not** measured operational security performance.
- **Read-only conformance kit.** A pilot structural report in JSON/Markdown (`playbook.conformance-report.v1`) that checks available task/envelope data, changed paths, declared capability metadata, evidence SHA equality, and approval-reference presence. It **always reports `effect_authorized=false`**.
- **Demonstrated representative adoption.** One tiny standalone Python case study with a bounded T2 change and a rejected authority-expansion path, not evidence of broad production adoption.
- **Governance evolution.** Canonical glossary, architecture decision records, compatibility/migration policy, and optional advisory guidance for learned decision/predictive models.
- **Provider-backed admission in this repository.** GitHub's own default-branch ruleset now requires pull requests and two source-pinned checks, with one deliberately failing PR observed as blocked. This **does not** automatically protect adopter repositories.

## How to evaluate the pinned package

After an authorized tagged release is published, clone/check out the **verified immutable release tag**; do not use a moving `main` checkout as release evidence. From that checkout with Nix flakes enabled:

```bash
nix flake check --print-build-logs
nix develop --command python3 scripts/conformance-kit.py --root . --integrity --format json
```

For the manual-first adoption path, start with [quickstart](../adoption/quickstart.md), [minimal adoption kernel](../adoption/minimal-adoption-kernel.md), [risk matrix](../task-risk-matrix.md), and [evidence standard](../delivery-evidence-standard.md). Adopters must set up **their own** repository protection, identity/tool constraints and approval processes. The conformance kit needs the pinned playbook dependencies and is an advisory structural check, not a stand-alone authorization token.

## Compatibility and migration

- **Initial release:** there is no prior tagged release with a guaranteed backward-compatibility promise.
- **Untagged `main` consumers:** inspect differences in copied envelopes, validators, PR templates and policies; do not assume old examples are valid under this schema or that `main` is stable.
- **Schema:** the existing JSON Schema ID points to a mutable branch URL; pin the actual release ref/commit rather than relying on that ID. Do not add `playbook_version` to envelope JSON/YAML without a separately reviewed schema change.
- **Evidence:** composite required levels are represented by the `required_levels` array; historical singular `required_level` is a deprecated reference, not a field accepted by the current schema.
- **Future 0.x upgrades:** externally observable policy/schema/template/evidence semantics require MINOR and explicit migration notes where affected; PATCH is for backward-compatible repair.

No secret, production data, signing credential, or runtime-authorization migration is required to consume these *documentation and structural tools*. A production downstream rollout must undertake its own risk assessment.

## Supported assurance and important limitations

| Supported by inspected evidence | Not established by this release |
| --- | --- |
| Structural task-envelope/schema checks and local validator tests | Truth of risk classification or binding approval |
| Pinned validation toolchain and exact-revision GitHub CI checks | Semantic correctness outside tested predicates or signed build provenance |
| Synthetic negative fixtures and one reference adoption | Production effectiveness, broad compatibility or measured false-positive rates |
| Read-only advisory conformance-report output | Independently authenticated execution of claimed CI evidence, grant enforcement or valid human approvals |
| GitHub admission for **this** repository, with failed-check proof | Enforcement on copied downstream repositories, direct-push/missing-check negatives, or protection against provider-admin ruleset changes |
| Source documentation, glossary and accepted ADRs | Independent security certification, production agent runtime, controlled release authorization or full end-to-end attestation |

The branch ruleset protects `main` but not annotated release tags; **tag immutability currently relies on controlled operator practice**.
