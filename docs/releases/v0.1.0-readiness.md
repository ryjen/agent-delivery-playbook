## Compatibility and migration disposition

This is an **initial version**, so there is no prior `v0.x` tag with a promised migration path. Consumers who copied material from untagged `main` must explicitly compare their local schemas, validators, templates and risk/evidence policy with the tagged commit. This PR **does not** alter task-envelope fields, T/E enums, evidence requirements or validation semantics.

The canonical task-envelope schema currently has a `$id` pointing to a mutable `main` path. Pin the release by **tag/commit** (and optionally digest), not `$id` or a mutable URL alone. Do not introduce an undocumented `playbook_version` field to make examples appear versioned. Conformance-report `schema_version` describes that report format, not authorization or a promise to accept all future report versions. Read-only `--format markdown` and `--format json` are advisory outputs.

Per the [pre-1.0 policy](../versioning-and-compatibility.md), breaking external semantics require new MINOR plus migration notes; PATCH releases are reserved for backward-compatible repairs. Published tags must never be retargeted.

## Operational caveats and post-release tasks

- **GitHub ruleset is repository-specific.** Adopters must configure their own protected admission/required checks; these controls do not follow by cloning a policy file.
- **Attestation, model identity, runtime grants, and approval validity are not verified.** A hash match, approval reference, green local CI run, or a model `NO_FINDINGS` result cannot confer authority.
- **Portability is bounded.** The included case study is representative, and the kit's own tests are not a separate implementation's production verification.
- **Coverage gaps remain.** Missing-check and direct-push negative scenarios were not individually tested. Do not mark either done based on PR #87.
- **Tag authority remains operator-held.** Branch ruleset `17832277` does not protect release tags; avoid long-lived or privileged publishing credentials in automation. Do not create a tag before exact commit approval.
- **Release does not claim production deployment.** Scope is methodology, portable artifacts, and tested structural checks; no production data or credentials are used.

## Release operator checklist — explicit post-PR procedure

- [ ] Freeze and name the exact **final candidate** commit. Confirm PR readiness review and final `main` SHA are current.
- [ ] Read required check conclusions, runner/lock/commit identity and final `nix flake check` output. Any new commit invalidates previous exact-head approval.
- [ ] Review normative vs illustrative artifacts, migration notes, outstanding limitations, sensitive contents, and [draft release notes](v0.1.0-notes.md); record acceptance or exceptions.
- [ ] Obtain **explicit accountable operator approval of that SHA and notes**. Documentation author/model reviewer/green CI cannot approve its own release.
- [ ] Authorized operator creates **annotated `v0.1.0` tag** pointing at that SHA (not moving an old tag), then publishes matching GitHub release.
- [ ] Independently read tag -> commit -> tree/`flake.lock` and published release notes; verify intended repository/provider identity and preserve audit references.
- [ ] Run tagged-checkout/consumer smoke validation and record result. If any check is missing or failed, leave that claim unqualified and file narrowly scoped follow-up work.

**No commands here automatically create a release, alter provider protection or expand runtime authority.**
